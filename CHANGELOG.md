# Changelog

## [Unreleased]

### Added

- **WebHostManager explains a refused port instead of printing one identical bind stack trace per host.** When hosts die on startup with a `SocketException` — 10013 (access denied) or 10048 (address already in use) — the fatal log now names the socket error, how many hosts it refused, the ports from `Firefall:WebHosts` plus the GRPC GameServerAPI port, and what refuses a bind on Windows in the order to check it: WinNAT's reserved port ranges (Hyper-V/WSL2/Docker Desktop, which move at every reboot — `netsh interface ipv4 show excludedportrange protocol=tcp`, `net stop winnat`, the persistent `netsh int ipv4 add excludedportrange` reservations), a leftover elevated `WebHostManager.exe`, and antivirus that only lets signed binaries listen. The README troubleshooting section gained the same walk-through for 10013 (and 10048).

- **Full zone population toggle: `WorldPopulationSpawnFullZone` spawns the full population across the entire zone, not driven by distance, and keeps all NPCs spawned without despawning.** When enabled in `App.config` (or through `GameServerSettings`), `WorldPopulationService` activates all planned cells in the zone simultaneously rather than streaming cells near players within `ActivationRadius`, does not despawn NPCs when players move away or leave the zone, and continues planning, spawning and maintaining zone population even with no players connected. Killed NPCs respawn in place through the normal reconcile and respawn delay pipeline. Configurable via `<add key="WorldPopulationSpawnFullZone" value="true"/>` (default `false`). Tests: `WorldPopulationServiceTests` (+6 cases: full zone spawning without distance limits, no despawning on player movement, spawning/keeping population with no players, no despawning when last player leaves, killed NPC respawn, and status reporting). Docs: `Docs/WORLD_POPULATION.md` §6.

- **Mobs and NPCs shoot the model, not above it: their ranged aim is now the middle of the target's collision volume, led for its movement, and drop-compensated for the parabolic rows.** A ranged NPC used to aim a fixed height above the target's feet (the eyes): the shot registered because a character's collision volume is forgiving, but the tracer visibly sailed over the model and still connected. `NpcAttackAim` (new) resolves the aim in three parts. *The point:* the centre of the target's current collision volume - `PhysicsEngine` now caches the middle of each collision compound per shape (`CompoundCacheEntry.AimCenter`, computed once per asset in `CreateActivePose`) and exposes it through the new `PhysicsEngine.TryGetCharacterAimPoint`, which uses the same pose resolution the body uses, so crouch, sprint, falling and prone are tracked; half the pose's own `PhysicsHeight` (the database's physics capsule) stands in when the shape does not resolve, and a mid-torso default when the row carries no height. *The lead:* the round spends its flight time in the air and the target keeps moving through it, so the aim leads the target's velocity over that time, settled against the shot's own flight time and clamped at 3 m so a bad velocity aims wide rather than across the map. *The drop:* for the ammo the simulation actually drops, the initial direction is the closed-form parabola through the led aim point - the exact curve `ProjectileSim` integrates (`start + v·t + (0,0,-g)·t²/2`, solved as a quadratic in `t²`, low arc preferred, high arc for a target below the muzzle) - instead of firing at the point the round would fall away from; an arc the speed cannot reach falls back to the straight shot, which is the old behaviour. The weapon's visible aim agrees with the shot: while a brain faces its target it points at the same model-mid point, so muzzle, tracer and impact go to the same place. The weapon's own first-shot cone is untouched and still scatters on top of the corrected aim. Tests: `NpcAttackAimTests` (the parabola lands on the aim through the sim's own integration at the same height, above and below the muzzle, with and without lead; the unreachable arc falls back; the lead clamps; the fallback heights). Docs: `Docs/NPC_AI.md` §3

- **Unmanned turrets aim the same corrected aim: from their own muzzle, at the middle of the target's model, led and drop-compensated.** The unmanned-turret AI (`TurretAi`) aimed from the turret's base at a fixed 1.4 m above the target's feet, which for a barrel sitting metres above its base shoots up and over the model; it never led and never compensated the drop. It now resolves the shot through the same `NpcAttackAim` the NPC path uses — centre of the target's current collision volume (half the pose's `PhysicsHeight`, else the mid-torso default), led for the target's velocity over the shot's own flight time and clamped at 3 m, and the closed-form parabola for the `Parabolic` ammo rows — from the lead barrel's own muzzle: the new `TurretWeaponFire.LeadMuzzleOrigin` resolves the first ranged row through the same shared `ResolveOrigin` the fire path uses per barrel (`PhysicalOrigin` + muzzle hardpoint, falling back to the gunner's chest), so the aim and the shot leave from the same point. `EyeHeight` remains for the line of sight cast only. The seated-gunner path is untouched: a gunner fires along their own aim packet. Tests: `TurretAiTests` (+3: a 2 m-high muzzle aims at the model's middle instead of the eye line, a 10 m/s target's lead clamping the aim point 3 m ahead, and a parabolic row's shot re-simulated through the same parabola `ProjectileSim` integrates landing at the model's middle)

- **`Docs/CLIENT_PERFORMANCE.md`: why the Firefall client pins a CPU on a modern machine, and what to do about it, in the order worth trying.** The client is a 32-bit DirectX 9-era executable from 2014 and does not scale past a couple of threads, so "8 cores / 16 threads" is not the headroom it sounds like: a high total is usually one saturated thread, and the doc says how to see that per-thread before changing anything. The first lever is one PIN owns — world population, on by default at `WorldPopulationMaxLiveNpcs` = 150 NPCs inside 150 m of a player, which is denser than the live game's authored spawn groups were, and every one of them is an entity the client scopes in, animates and simulates. Then the client-side ones: `[VOIP] Enabled = false` in `firefall.ini` (the best-documented 2014 fix, worth making the file read-only), the texture streamer's own CPU cost — which is being paid for nothing at all when the sharp mips are absent — a fixed Dynamic Resolution and a framerate cap instead of an uncapped main loop, core parking on a many-core processor, and the settings that were CPU-bound in 2014 (shadows first). It ends with a bisect: turn the population off, then VOIP and the cap, then look at whether it is one thread or many. Linked from `Docs/README.md`.

- **Data-backed ambient NPC routines, not invented original patrols.** Declared wanderers now move on checked ground, honour explicit distance/gait/pause/leash settings, return after combat, and can reserve/visit real placed work/rest deployables. 508 prod-1962 templates resolve to wandering; one explicitly requests distance zero. Unknown/named-route/climbing definitions stay unresolved rather than receiving arbitrary walks. Shared navigation checks every movement step for holes, cliffs, exclusions and body clearance, caches ambient corridors and bounds new searches/catch-up displacement. `\ai routines` reports coverage/ground status; `\ai list` includes routine states. A reproducible census names all 575 tables and includes every movement invocation/reference from all 3,109 monster rows; Python and C# tests enforce it in CI. **Not full original-game parity:** CAIS trees/authored routes are missing, and the captured world has no placed emote-bearing work stations. See `Docs/NPC_ROUTINES.md` and `Docs/NpcMovement/README.md` for supported inputs, explicit compatibility defaults and the exact limits.

- **Zones are now populated with every mob and NPC the database puts there: `WorldPopulationService` streams a plan of the loaded zone around the players in it, on by default (`SpawnWorldPopulation`).** A zone used to hold only the entities `character_spawn.json` authors. The shipped `clientdb.sd2` has no per-zone spawn table — that lived in the live server's spawn groups, which never shipped, and nothing else in it carries per-zone monster positions (`MissionWaypoint.location` is chunk-local ±256, the faction tables have no zone link) — so both halves are derived from data that *is* there. **Which rows:** `MonsterHabitatClassifier` admits 2,853 of the 3,109 `dbcharacter::Monster` rows (89 have neither a `chassis_id` nor a `posetype_id`; 167 ask for a behaviour that is not a world inhabitant — `Null`, the pets, the engineer turrets and teleporters, `Elevator` / `DoorUpInteract`, the dev leftovers — read through `NpcBehaviorParams.Parse`, so a behaviour classifies on its name and not its arguments) and sorts each into `Wilderness` / `Settlement` / `Melding` from its `behavior`, its faction's `internal_name` (`melding`; `chosen` fits both, because the Chosen come through the Melding and patrol around it) and its `vendor_id`: 1,023 settlement, 1,731 wilderness, 351 Melding. **Where:** `WorldPopulationPlanner` accumulates the zone's navigation-mesh face centroids — walkable slope and `exclude_from_pathing` already applied by the bake, now enumerable through the new `NavigationMesh.TryGetFaceCentroid` / `PhysicsEngine.TryGetWalkableFaceCentroid` — into 32 m cells centred on the ground that landed in them, refuses the cells whose chunk the zone's own metadata says the server does not simulate (`ZoneChunkLinker.clientonly`, newly loaded, and `ChunkRecord.remove_in_production`; Coral Forest has 64 server-side chunks of its 93), and takes each cell's habitat and level from the authored anchors the server already spawns the zone from — outposts with their own 150-550 m radius, the 469 deployables, the 16 Melding perimeters — a settlement beating the Melding around it, and the level being the band of the *nearest* banded anchor however far away, which is what reproduces the original gradient (Coral Forest: 1-5 at its starter outpost, 29-30 in its far corners, where the zone band alone says 1-30). A zone with no walkable surfaces falls back to the anchor positions and says so. **How many:** a coverage pass gives every admitted row one slot somewhere it fits, exempt from the difficulty budget so no row is priced out of its zone (rows the zone cannot host, and rows past the plan's slot ceiling, are counted and reported), then a density pass fills the remaining room in a hash-scattered cell order, picking rows by the frequency their `difficulty_cost` implies and charging it against 400 per cell (25 for a row that carries none) — common ambient rows in groups, expensive ones alone. `ai_spawn_delay_ms` is the delay between a cell activating and its NPCs appearing; `body_radius` / `body_height`'s `-1` sentinel (3,103 rows) resolves to the AI's own 0.7 m / 1.8 m agent numbers. **Collisions, both kinds, before anything appears:** the physical one — the new `PhysicsEngine.TryGetGroundSurface` (ground probe 1.5 m up / 3 m down, the AI's own reach, so a validated spot is a fixed point of its snap) with the mesh's `|normal.Z| ≥ 0.35` cutoff, plus the new `IsStandingVolumeClear` (ankle/waist/shoulder probes, headroom, broad-phase query for the bodies already in the box) — and the server-side one, `SpawnOccupancyGrid`: a spatial hash of the bodies that are *planned but not spawned yet*, which no ray can see and which is how a cell would otherwise stack its four NPCs in one spot the instant they all appear, plus 25 m of clearance from every player before and after the snap. A refusal is retried at jittered positions and then a second later; a slot whose *ground* never accepts it is parked after 8 rounds and reported, while one refused only for *room* keeps waiting. Spawning goes through `EntityManager.SpawnCharacter` with the new `snapToGround: false` (the spot is validated; the engine's own snap searches 10 km down and would move it onto a roof) and `scopeToNearbyClientsOnly: true` (the "introduce every new entity to every client" hack would send hundreds of mobs to players the scope check retracts seconds later). **Bounded:** 600 live NPCs, 12 spawns per 100 ms (an order of magnitude under the entity manager's 800/s scope-in drain), one update per 250 ms, and a work budget the plan is built under (20,000 faces *or* cells per update — classification against the anchors is the expensive phase, so it is spread too). Cells activate inside 200 m of a player and deactivate beyond 300 m; a zone with no players plans nothing and holds nothing, and everything this system spawned is removed when its last player leaves or the feature is turned off — the zone's own entities are never touched, and `Despawn` refuses to remove anything it did not spawn. An update that throws is caught and counted and the feature turns itself off after three in a row; a row `SpawnCharacter` cannot build is caught per row, reported once, and its slot parked. Plans are deterministic end to end (roster order, cell order, jitter, facing and density picks all hash from the cell key and slot index), so the same database and zone give the same world and a reactivated cell shows the same NPCs in the same places. Runtime: `\population on|off|status|near [radius]` in chat and on the admin channel, both spellings running one shared `PopulationCommand`. Tests: `MonsterHabitatClassifierTests`, `SpawnOccupancyGridTests`, `WorldPopulationPlannerTests`, `WorldPopulationServiceTests` and `Fakes/WorldPopulationFakes.cs` — the four seams (`IWorldPopulationDataSource`, `IWorldPopulationTerrain`, `IWorldPopulationSpawner`, `IWorldPopulationRules`) let the plan and the streaming be asserted on without a loaded `clientdb.sd2` or a zone with collision. Docs: `Docs/WORLD_POPULATION.md` (new), linked from `Docs/README.md` and `README.md`.

- **`SwitchWeapon` (aptitude command 97) is implemented: the weapon-swap effects of 74 abilities now actually swap the weapon, with the draw animation when the row asks for it.** The command sat behind a commented-out `Factory` case with a `return true` placeholder body, so every "hold this weapon while the ability is out" effect in the build (299 of the 302 effects whose chains carry an instance — 1,418 `dbitems::AbilityModule` loadout-module rows reach them) selected nothing. The command now writes the character's replicated weapon selection (`WeaponIndex` on the entity, the combat view and the combat controller) to the row's `TargetWeaponSlot` — slot 1/2 the equipped weapons, 3 the slot an ability-granted weapon occupies; the server resolves no item for index 3, the client does from the same row. It runs in the command itself (apply, update, remove and ability chains all execute it), `restore_on_rollback` (202 of 343 rows) registers the active that hands the previous selection back when the effect is removed — only while the weapon is still the one the command switched to, the same "only undo what this row owns" rule `CombatFlags` applies to its bits — and `play_animation` (204 rows) stamps the combat view's `EquipmentLoadTime` at the swap, the one equip-timing field on the wire, written once at spawn until now. A switch takes the scoped state with it, the same rule the player's own `SelectWeapon` packet is handled with. **What is documented instead of implemented:** `Forced` (156 rows) has no distinguishable server-side gate (the selection is plain replicated state; both values switch), and `ForcePush.do_animation` stays documented with the wire evidence in `Docs/EMOTES.md` §6 — the protocol's animated-movement type (`Bullrush`, 6) would gamble the verified glider-pad launch on an unobserved client behaviour, and the rows carrying the flag include the pads themselves. The stale §6 note about `ApplyClientStatusEffect` / `RemoveClientStatusEffect` being unwired is corrected (both have been constructed by `Factory` and apply/remove through the shard's `AbilitySystem`). Tests: `SwitchWeaponCommandTests` (the swap on all three replicas with the row's time, the equipment-load stamp and its absence, restore-on-rollback with a fresh time, the player's mid-effect weapon choice left alone, no restore without the flag or without an actual switch, the negative-slot step-over, the deployable step-over). - **Player shots are now visible to other players: `CombatController.FireWeaponProjectile` still echoes `WeaponProjectileFired` to the shooter on ReliableGss, and now also announces that same packet (time, aim, velocity) to every other client scoped into the shooter.** A player's own client predicts the tracer from the fire input, which is why the echo was shooter-only; everyone else watching that character used to see the burst markers (`FireBurst` / `FireEnd` already replicate on CombatView) with no tracer. `ProjectileFiredAnnouncement.SendToWatchers` takes the pre-built message and `exceptOwner: true` so the shooter is not sent a second UnreliableGss copy (`EntityManager.SendToScoped` includes the character's own client). NPC and turret fire keep the default (`exceptOwner` false): they have no CombatController echo, and a seated gunner only sees the shot through the launcher announcement. - **Unmanned turrets now shoot, dual-weapon turrets fire every ranged barrel, ammo replicates, the muzzle follows the turret pose, and the gunner's frame level scales damage.** `TurretAi` (owned by `AiEngine`, registered from `EntityManager.SpawnTurret`) ticks **before** the empty-brains early return so a shard with no NPCs still fires; `Enabled` / `_rules.Enabled` gate it too. A seated turret (`ControllingPlayer != null`) is left to the gunner's `FireWeaponProjectile`; an unmanned one picks the closest hostile player inside the lead weapon's `AttackRange` (not the NPC `AggroRadius` of 55 m) and fires at that weapon's `AttackIntervalMs`. The projectile source is the parent `CharacterEntity`, else the parent `BaseAptitudeEntity.Owner` (deployable / vehicle); the owner is skipped so AlwaysHostile cannot shoot them, and a dead parent deployable or a missing source is silent. `dbcharacter::Turret.Behavior` is a numeric flag, not CAIS. `TurretWeaponFire` now walks every ranged `TurretWeapon` row of the type (21 dual-weapon types in prod-1962; melee / unresolved rows skipped; round index = barrel index for the PRNG), rotates `PhysicalOrigin` by the current pose (`QuaternionEx.Transform(offset, Inverse(rotation))`, identity leaves the existing world-axis tests), and scales `DamagePerRound` by the gunner's `FrameProgressionLevel` through `WeaponDamageMath.DamageLevelScale` (the resolver stays level 1 / `monsterId` 0). Remaining ammo is a `ushort[]` on the controller (`AmmoData.Ammo`) with slot indices on the observer (`AmmoStruct.AmmoIndex`); the turret protocol has no `ReloadWeapon`, so an empty clip refills before the round rather than blocking. **What is documented instead of implemented:** `MuzzleHardpoint` (`dbvisualrecords::Hardpoints.Transform` is not loaded), `AnimationUpdated` (unnamed `ushort`+`byte` on Character ObserverView, never sent), overcharge (`MsOverchargeDelay` / `OverchargeAbility` have no AI/turret trigger; charge is client-side). - **A seated turret now fires its own `dbcharacter::TurretWeapon` through the same projectile path an NPC rifle uses, instead of doing nothing.** `Turret.BaseController.FireWeaponProjectile` was an empty `// todo` (the burst markers from `FireBurst` / `FireEnd` already played, but nothing ever left the barrel), and the 149-row `TurretWeapon` table was loaded as a record and never walked. `TurretWeaponFire` resolves each `dbcharacter::TurretWeapon` row of the turret type through `NpcAttackResolver.ResolveWeapon(monsterId: 0, weaponId, level: 1, NpcBehaviorParams.Empty, Vector3.Zero)` - the method already documented as public for deployables/turrets - and hands one round per ranged row to `ShardAiProjectileLauncher`. `monsterId` 0 keeps the creature damage modifier at 1 (a turret is not a monster); the gunner is the projectile source (hostility, combat log, the watching-client `WeaponProjectileFired`); the shot leaves from `TurretWeapon.PhysicalOrigin` rotated by the turret pose, falling back to the gunner's own projectile origin when the row has none. A melee or unresolved row, a degenerate aim, and a packet from anyone but the seated gunner all no-op. The gunner's equipped weapon is not fired. The table is now loaded (`StaticDBLoader.LoadTurretWeapon`, grouped by `TurretTypeId`, ordered by `Id`; `SDBInterface.GetTurretWeapons` returns an empty list when the type has none) and `sdbinfo turret` lists the weapon ids. - **The last two weapon-template ability hooks the database names a trigger for now run: `melee_ability_id` is the attack when burst and attack are empty, and `reload_ability` fires when a reload starts.** A melee weapon that only fills `melee_ability_id` used to store the id and never scan or activate it, so its swing chain never applied; `NpcWeaponAbilities.Scan` now walks it as the third attack id (default 0, so every existing attack+burst call is unchanged) and `AiEngine.ActivateWeaponAbility` picks burst, else attack, else melee (`NpcAttackProfile.AttackChainAbilityId`) - the same order a player weapon already prefers for that window, which is why Shadowstrike (burst 188) is untouched and a leftover melee id cannot steal it. The reload column was not even on the profile: it is the sibling of `clip_empty_ability` (the empty click is the moment the magazine runs dry, this is the reload that follows), scanned with a fresh visited set like the empty hook, carried as `ReloadAbilityId` / `ReloadClientFeedback`, and activated from `StartReload` when the chain carries client feedback - both the dry-after-burst path and the `CanFire` path that starts a reload that was never announced. A server-only reload chain is left alone, exactly like a server-only empty-clip or burst chain. The `WeaponReloaded` marker is still what the client plays `anim_reload_type` from; the extra chain is the one the row names for that same window. **What is documented instead of implemented:** `overcharge_ability` (the plasma/fusion cannons still state a delay without an event); `AnimationUpdated`; stumble/hit-reactions (0 hardpoint rows); dialog/battle-chatter. Tests: `NpcWeaponAbilitiesTests` (melee-only scan), four `NpcAttackResolverTests` cases (melee walked, burst preferred over melee, a client-feedback reload hook, a server-only reload hook) and four `AiEngineTests` cases (melee-only activation, burst preferred over melee, the reload hook firing once per reload, a server-only reload never running). Docs: `Docs/NPC_AI.md` §3/§6.

- **NPC shots now scatter inside the weapon's own spread cone, the same first-shot number a standing player would get from the same row.** A ranged burst used to fire every round along one chest-aimed ray, so a shotgun's pellets stacked and a rifle could not miss as long as line of sight held: the template's `min_spread` / `max_spread` / `starting_spread` (with the item's attribute 958, Weapon Spread, scaling both terms the way `WeaponSpreadProfile.Build` scales them for a player) sat on `WeaponTemplateResult` and were never read. `NpcAttackResolver` now carries them on `NpcAttackProfile` (`MinSpread` / `MaxSpread` / `StartingSpread` / `SlotIndex` / `SpreadPct`) and `AiEngine.FireRangedAttack` spends `SpreadPct` through the same `PRNG.Spread` a player shot uses, once per round, seeded with the shard time, the template's `slot_index` and the round number. The cone is the standing first-shot number (`MinSpread + StartingSpread × (MaxSpread − MinSpread)`), not a running heat state: an NPC rests between bursts for the behaviour's `fireRestDuration` (median 1,000 ms across the build's ranged humanoids), which outlasts every `ms_spread_return` the NPC weapons carry, so there is no heat to keep and inventing one would make those mobs less accurate than the row describes. A weapon the database gives no spread (every melee row, and the ranged rows whose min/max/starting are 0) still fires along the aim, which is what those rows asked for and what the existing identical-direction tests pin. Aiming straight up or down no longer produces a degenerate `aim × world +Z` basis (the fallback is `aim × world +X`). **What is documented instead of implemented:** the rest of a player's spread state - accumulated heat, `spread_per_burst`, movement add, agility, crouch - because an NPC does not hold the trigger; ammo impact abilities (`Ammo.ability_id` / `touch_ability_id` / `airburst_ability_id`) still unused. Tests: `NpcAttackSpreadMathTests` (new: the standing first-shot formula, attribute 958 scaling, a 0 row, per-round scatter, determinism, and the vertical-aim fallback) plus two `NpcAttackResolverTests` cases (the cone on the profile, attribute 958) and two `AiEngineTests` cases (a 0 cone keeps every round of the burst on the same ray; a non-zero cone scatters them). Docs: `Docs/NPC_AI.md` §1/§3/§5/§6, `Docs/SPAWNING_AND_COMBAT.md` §3

- **Web assets now have roots the operator can name, and the asset host says what it will and will not serve before anyone launches a client.** `WebHost.WebAsset` was a `UseStaticFiles` over `<content root>\Assets`, and nothing else: no way to point it at the assets already on the machine, and no word when that folder was empty - which it is in every checkout, because `.gitignore` keeps Red5's multi-gigabyte game data out of the repository (nothing inside is tracked but a `.gitkeep` and the `README.md` that explains what belongs there). The consequence is the one a player blames on the server's resolution and not on a path: the client probes `VTRemotePath` for the high-resolution virtual-texture chunks (`HEAD /vtex/%ENVMNEMONIC%-%BUILDNUM%/static.vtex0`, then `.vtex1` and `.vtex2`; `prod-1962` for the Steam build), gets three 404s, and keeps the low-resolution mips baked into its own archives - blurry terrain at *every* graphics setting, because the setting drives the streamer and there was nothing to stream. Three things changed. **`Firefall:Assets:Paths`** (new `FirefallAssets`, bound from `config\appsettings.json`) adds asset roots after the default one, searched in order, first match wins, relative paths anchored at the same content root - so a server can serve the chunks out of the client's own `system\vt` instead of carrying a second 12 GB copy, and `Shared.Web/Assets/WebAssetFileProvider.cs` composes them into one namespace (a missing folder is skipped instead of throwing `PhysicalFileProvider`'s exception, and the change token never fires because a filesystem watcher per root over twelve gigabytes buys nothing when every static response already carries `Last-Modified` and an `ETag`). **Unknown extensions are served**: `ServeUnknownFileTypes` was off, and `StaticFileMiddleware` rejects an unrecognised content type *before it looks at the disk*, so `.vtex0` stayed a 404 even with the file at exactly the path the client asked for - the single default that made "I copied them into Assets and nothing changed" true. **A startup report** (`Shared.Web/Assets/AssetRootProbe.cs`, with `VirtualTextureChunks` owning the path shape it recognises) names each root, the chunk files it holds with sizes, the builds it can answer for and which chunk of the set it is missing - and warns `Blurry textures ahead: no asset root holds a chunk file for a client to fetch - <roots>` with the folder to fill in, the answer that previously meant reading the client's source. Chunks are also served for a request that no root answers literally: `vtex/prod-1962/static.vtex0` is retried by file name - at the top of a root, then directly inside its `vtex` folder - because the build in that path is a property of the *player's* install and not of the data, and `static.vtex0` flat in `Assets\` is both what a person who read "put the vtex files in the Assets folder" produces and what the client's own `system\vt` folder holds; the fallback is scoped to `static.vtex0/1/2` (`VirtualTextureChunks.Candidates`), so no other path can be answered by a file it never named, and a file at the literal path always wins over a loose one. - NPC and mob weapons now **reload**, and the reload is what plays the weapon's reload animation. A player's reload is client driven (the client sends `ReloadWeapon` / `CancelReload` and the server only relays the two times into `CombatView`), so a mob - which has no client to send them - used to fire forever: `AiEngine` now keeps the weapon's magazine itself in the new pure, unit tested `NpcWeaponMagazine` and produces the same markers a player's own reload does. The evidence turned out to exist - `themeldingwars/Documentation`'s `Captures/2015-05-02 - 1869 - Gameplay.pcapng.gz` holds one complete live vendor session (terminal 60, "Copacabana ARES Supplies", store 2321), whose 3,006-byte `VendorProductsResponse` decodes to 32 rows with every price, both reputation gates, the store's title, its faction and its three discount rungs - so `LiveVendorData` (new) carries that recording as data and every vendor answer is built from three tiers of it, each row stamped with where its numbers came from (`VendorDataProvenance`: `Captured`, `DatabaseDerived`, `Emulated`). **Captured stores** replay row for row, in window order, and nothing is derived for or added to them. **Token machines** (vendor ids that are `dbitems::VendorTokenMachine` ids - monsters carry 5 and 105) list their `VendorTokenDisplayItems` prizes at one `VendorTokenKeyItems` token each. **Every other vendor** - some seventy quartermasters in prod-1962, whose store catalogs were server-only and did not survive, and where a census of all 575 tables' columns found no price for vendor goods anywhere - now stocks *the captured store's field supplies*: the eleven rows live sold ungated, each at its recorded price (scan hammer 50 cy, health packs 100/500/2500, ammo pack 100, the four grenades 150, adrenaline injector 250, glider pad calldown 150), then six consumables PIN already stocked whose prices stay chosen and say so. one payout per slot the machine has (machine 5 has two: 5853 "Slot 1 (Crystite)" and 5857 "Slot 2 - 'Rare Item' % check", which machines 105/106/107 share at `loot_table_scale` 1.3/1.6/2.0), each table taking one of its item and sub-table rows by `probability` out of the sum of *its own* rows (slot 1's five crystite rows sum to exactly 1000, the tables under slot 2 to 9, 22, 32, 48 and 1000 and slot 2's branches to 850 - Quality and level rolls, `LootTableDistRequirements` and `roll_mode` are not modelled because no table a machine can reach authors any of them, and a machine that awards nothing still takes the token and says so in the log. - **The web hosts bind every interface and the addresses they advertise became configurable, so a second player can join over LAN or a VPN.** Two separate things kept PIN a single-machine server. Every Kestrel host listened on `localhost` only — `Firefall:WebHosts:<host>:urls` in `WebHosts/WebHostManager/config/appsettings.json`, applied through `UseUrls` in `BaseWebServer.Build` — and the two responses the client learns addresses from hardcoded it as well: `CapabilityRepository` answered `GET /check` with eleven `https://localhost:443xx` host URLs, `OracleController` answered `POST api/v1/oracle/ticket` with `MatrixUrl = "localhost:25000"`, `Datacenter`/`Hostname = "localhost"` and an operator override for the ingame/clientapi hosts. Open sockets were never the whole story: `localhost` resolves to the *client's* machine, so a player on a second PC was sent to himself however reachable the server was. Bind addresses now default to `*` (IPv4 `0.0.0.0` and IPv6 `[::]`, chosen over the bare `0.0.0.0` so a local client on `localhost` keeps working over IPv6 too), and both responses build their URLs through the new `Shared.Web.Config.PublicUrls` from `Firefall:PublicHost` — the single setting that names the address players reach the server on, `localhost` by default so an existing local setup is untouched. Each advertised port is taken from that host's configured bind urls rather than a literal, keeping the configuration the only source of truth for ports, and the scheme follows `Firefall:AdvertiseHttps`. The oracle ticket is the load-bearing one: the MatrixServer's `HUGG` reply (`MatrixPacketHugg`) carries a sequence start and the GameServer *port* — no IP field — so the client dials the game at the matrix address, and `PublicHost` covers the UDP connection with it. `AdvertiseHttps = false` also skips `UseHttpsRedirection`, which with a TLS address bound answers every plain request with a 307 to the https port that a remote client cannot follow without trusting PIN's self-signed development certificate, and `Firefall:Certificate:Path`/`Password` make Kestrel serve a `.pfx` whose SAN matches the advertised address instead of that dev certificate (`X509CertificateLoader.LoadPkcs12FromFile`; an empty path keeps today's behaviour, an unreadable file is logged and skipped rather than taking the hosts down). The `Firefall` singleton registration is null-guarded so a missing section falls back to the defaults instead of killing DI. Both UDP servers already bound `IPAddress.Any`; the GRPC port 5201 is server-internal and documented as one to keep closed
- **Accounts start fresh: creating one no longer duplicates the admin account's characters to it.** The account system's first cut seeded every account with its own copy of the 38 zone-picker entries on first sight (`CharacterStore.EnsureSeededForAccount`, called from both the character list and the creation flow), so a brand-new account — the Steam-provisioned one, a `POST api/v2/accounts` one — opened the selection screen already showing the same "characters" as admin: the zone picker, 38 times over, per account. The zone picker is now what it was always meant to be, the **admin account's dev tool**: only the built-in admin account carries the seeded entries, every other account starts with an empty list and the client walks its player into character creation — the authentic new-account flow. Stores written by the old behaviour are migrated on load: untouched seed copies of non-admin accounts are removed (`CharacterStore.StaleZonePickerSeeds`, logged at `Warning` with a count), while created characters, the admin's entries and hand-added entries with non-seed names are never touched. The one-character-per-account ceiling that came with the old "the created character takes over the single spawn-zone slot" scheme is gone too: creation now takes the account's **next free slot** (`CharacterStore.CharacterGuidForSlot` — slot 0 keeps the guid a created character always had, slots above it add their index in bits 48..55 of the generated range, keeping the spawn zone in the low 16 bits the GameServer reads), so a fresh account can create as many characters as its limit; the limit itself is now enforced server-side (`ERR_DUPLICATE_CHARACTER` past the account's `CharacterLimit`). `CharacterStoreTests` covers the slot guids, the pruning predicate and the resolution of same-account slots end to end. Docs: `Docs/ACCOUNTS.md` §1/§6/§7/§10, `Docs/CHARACTERS_AND_BATTLEFRAMES.md` §1/§3
- The shard loop is paced instead of spinning. It ran unbounded — a full core at 100% even on an idle shard, and the usual PIN setup runs the server and the game client on the same machine, so the spin came straight out of the client's frame budget. `Shard.RunThread` now targets a 5 ms cadence with a hybrid wait (coarse `Thread.Sleep` while a comfortable margin remains, `SpinWait` for the last ~2 ms); every subsystem is gate- or accumulator-driven, so a late iteration only shifts gate boundaries, and the fastest gate (the 5 ms entity update flush) keeps its intended rate. This also makes the loop's per-iteration subsystem calls 200 per second instead of tens of thousands
- The network tick ran every ~50 **microseconds** instead of every 50 ms: `ShouldNetworkTick` compared `_networkTickRate = 1.0 / 20.0` — a value in seconds — against a delta in milliseconds, so the gate was always open and every client's queues were drained, flushed and acked on virtually every spin of the loop. The gate is now `_networkTickIntervalMs = 10.0`, milliseconds on both sides: twice the cadence the constant was meant to express, bounding a movement confirm (MovementInput → ConfirmedPoseUpdate on the wire) to ≤ 10 ms of queueing
- Dead clients are now retired. Nothing removed a client that vanished without a `CloseConnection` (crash, network drop, alt-F4): it stayed in the client map and scoped to every entity it could see, so pose broadcasts and view flushes kept allocating and sending to a ghost forever — and `NetLastActive` could never notice because *sends* keep refreshing it. `NetworkClient` tracks a receive-only `NetLastReceive`, and `Shard` sweeps every 5 s: a full 60 s of one-way receive silence sends a best-effort `CloseConnection` and runs the normal `MigrateOut` cleanup (test fakes, which are not `NetworkClient`s, are skipped)
- The UDP sockets disable `SIO_UDP_CONNRESET` on Windows (Linux never had the behaviour): Windows surfaces the ICMP port-unreachable of a peer that vanished as a `WSAECONNRESET` error on the socket's next `SendTo`/`ReceiveFrom`, so every send to a dead client threw and logged until the sweeper above noticed. Best-effort with a fallback to the existing error handling on platforms where the ioctl is unavailable
- `BaseAptitudeEntity.GetActiveEffects()` fast-paths the empty case. The 32-slot copy (nulls included) ran for every entity on every 20 ms ability-system tick and again for each aptitude command touching effects — the biggest single allocator on a populated shard. Callers all null-check each entry, so an empty list is exactly what the all-null copy gave them; entities with at least one effect still get the same snapshot as before
- Queued scope-ins are sent in batches of 16 per 20 ms gate instead of one per gate: a login in a populated area streamed the surrounding entities in at 50 per second — seconds of visible pop-in — where the batch finishes a typical login's scope-ins in well under a second at the same reliable-channel pacing
- Shape-resolution warnings stopped being a per-packet affair. `PhysicsEngine.GetCharacterPoseAsset` logged its "no collision/pose data" warning inside the shape *lookup*, which the engine re-runs on every movement update and every physics tick of an entity — one malformed database row therefore produced a warning per movement packet from its victim (and the sibling "no suitable collisionId" warning did it without even naming the entity). Both warnings now fire once per entity, name it, and their bookkeeping lives as long as the body does (pruned in `RemoveEntity`). The `UpdateEntity`/`RemoveEntity` hot checks also collapsed from a `ContainsKey` + indexer pair into single `TryGetValue` lookups.
- Server log files are bounded. Both Serilog rolling file sinks (the master log and the per-system map logs) rolled by day with no retention limit, so an always-on shard accumulated every day of Verbose-capable logs on disk forever; both now keep the last 31 files.
- The physics dispatcher fleet is capped at 4 threads. A zone shard's 20 Hz timestep of mostly static geometry plus a few hundred kinematic bodies does not keep a large fleet busy — every Bepu dispatch thread is a spinning worker competing with the game client for a core (`ProcessorCount - 2` of them on a typical machine), and the same server-plus-client-on-one-machine setup pays for all of them
- The physics timestep caps its catch-up at 8 fixed steps per shard tick and retires accumulated time beyond that. `TimeAccumulator` grew freely while the shard thread was blocked (zone loading, a long GC pause), and the tick after such a stall ran every missed 50 ms step back to back — hundreds of timesteps, which stretched the tick further and fed the next backlog: a self-sustaining spiral of death on exactly the machines (server and game client sharing cores) where stalls happen. Slowing simulation under overload is what every gate-driven subsystem of the shard already does; the physics loop now does it too, with a Debug note of the dropped milliseconds.
- Third hot-path pass: everything that still stood between a socket byte and a controller handler. `Deserializer.Read<T>()` — the entry point of every incoming packet's typecode, entity id, sequence number and control-packet reads — went through a boxed object return, a `GetCustomAttributes()` scan of the value type and an `Enum.ToObject` hop per read; it now has compile-time-dispatched primitive and enum fast paths (same wire encodings, including `Encoding.ASCII`'s replacement rule for `char`). `Channel` built each outgoing header from three throwaway `Serializer.WritePrimitive` arrays with a box each (per message: view changes, keyframes, command answers); the header, sequence number, matrix message id, controller-player ids and checksums are now written straight into the buffer with `BinaryPrimitives` — byte-identical output. The per-packet `Channel.LastActivity = DateTime.Now` stamping was dead (never read) and is gone, `HandlePacket` reads the clock once per datagram instead of twice, and the ack-latency `Verbose` log no longer evaluates `DateTime.Now` per reliable packet at log levels that drop it. Controller dispatch (`Base.HandlePacket`) ran every game message through `MethodInfo.Invoke` with a fresh `object[]` and a boxed entity id; the dispatch table now holds compiled delegates for the uniform handler signature (a reflection fallback stays for any handler that ever changes shape), and unhandled messages no longer resolve names and typecodes through the GSS tables when `Warning` is off. A typecode that routes to no controller used to re-scan the assembly reflectively **on every packet carrying it** — `Factory` now remembers unresolved (ns, ordinal) pairs. `EventBus` allocated a `ToArray()` snapshot per publish and delivered queued events through `Delegate.DynamicInvoke`; handlers are copy-on-write arrays now and queued events carry a prepared unboxing invoker, with subscription/unsubscription under a lock (the old bare `Dictionary` + `List` mutation from two threads was the actual bug that snapshot was working around). `MovementRelay`'s pose broadcast builds its `JumpActioned` once per movement input instead of once per nearby client, and `Serializer` stops allocating twice per float/double write (`MemoryMarshal.Cast` + `ToArray`) and copies fixed blocks per byte instead of per block.


- **Plain requests are no longer bounced to the TLS port; `Firefall:RedirectHttpToHttps` decides that.** `UseHttpsRedirection` used to be tied to `AdvertiseHttps`, so a server advertising https answered every request on its http port with a 307 to a TLS endpoint — a redirect the game client has no reason to follow and every reason to fail (the certificate on the other side was exactly the thing a remote player did not have yet), including the one request that can never be conditioned on it: the `certificate.cer` download that would have fixed that. Both ports answer what they are asked for, the client dials whatever it is told, and the http half is now simply usable; anyone who wants the redirect sets `RedirectHttpToHttps` and the two certificate routes stay plain even then (`BaseWebServer.IsCertificateRequest`). Related: `PublicUrls.Url`/`Port` gained an explicit-scheme overload (`Url(host, path, scheme)`, `PlainUrl(host)`) because the plain port of a host is now something to name in a log line while https is what is advertised, and `PublicUrls.IsLoopback` moved to the new `Shared.Common/ServerAddress.cs`, which is also what decides whether a certificate has to be issued — the web and the certificate halves of that judgement had better agree

- **Fourth hot-path pass: the per-NPC fixed costs that a density knob cannot remove.** The report that started this was "I lowered the population density and a populated zone still pins the server tick — ping and connection problems while walking around". The density brakes bound how many NPCs exist; none of them bound what each existing NPC spends per tick, and that spend was dominated by physics ray casts. Three changes cut it. **Line of sight is sampled on the perception cadence, not polled every movement tick.** `AiEngine.UpdateBrain` asked `HasLineOfSight` — a full ray cast against the zone's static geometry — for every engaged NPC on every 50 ms tick (and the give-up timer already tolerates a 200 ms staleness, and the brain's acquisition-from-idle rule required a sighting on the perception pass anyway). The verdict is now cast on the perception pass, on the first pass a brain reasons about a target, and when the target changed since the last cast (`NpcBrain.VisibilityCheckedFor`), and read from the cache in between. **The six-ray wall clearance probe runs every other movement tick and spans the gap.** `NpcGroundMovement.TryStep` checked every movement step for holes, cliffs, exclusions *and* static body clearance (six rays: two heights × three offsets, against the zone's statics); for a walking NPC that was the bulk of its cost, at 20 Hz per NPC. The probe now runs at 100 ms (`WallProbeIntervalMs`) and measures from the position it last covered to the new one (`NpcNavigationAgent.WallProbeOrigin` / `HasWallProbeOrigin` / `ProbeWalls`), so the skipped tick's movement is what the next probe checks — at chase speed one 100 ms gap is under a metre, shorter than the probe's own lateral offsets — while the ground-support check still runs on every tick, so an NPC never leaves the terrain between wall checks. A failed step keeps its probe origin (the unmade span is checked again), and a new route (`NpcNavigationState.Reset`) probes immediately, because its first direction was never probed. **The view-change flush runs at 50 Hz instead of 200 Hz.** `EntityManager` walked every entity of the zone and checked the dirty state of every view it replicates every 5 ms; health, ammo and effect deltas read no faster for a client, and the pose — the one update a player can see stutter — flows on its own `CurrentPoseUpdate` stream, not through that flush (`_updateFlushIntervalMs` 5 → 20). Two smaller ones: the acquisition scan (`RefreshTarget`) no longer re-enumerates the client map and re-tests liveness and zone per brain per pass — the shared half is collected once per perception pass (`CollectAcquisitionCandidates`), leaving hostility as the per-NPC half; and `CharacterEntity.RefreshMovementView` skips the new `MovementData` allocation and the dirty mark when position, orientation, aim and movement state all failed to change, which was paid on every AI tick of every NPC — most of a populated zone's NPCs standing still (the `Time` field only feeds the keyframe path, which serializes current values, so the skip is wire-identical). The net effect is that the per-NPC fixed costs the density knobs could never remove are a fraction of what they were: line of sight is cast on the 200 ms perception pass instead of every 50 ms tick for an engaged NPC, a walking NPC probes its walls half as often (a chasing one pays the same total, over a span it can now cover), an idle NPC no longer allocates its movement view every tick, and every entity's view flush runs at a quarter of the old frequency. Docs: `Docs/NPC_AI.md` (the sight bullet and the wall-probe paragraph), `Docs/CLIENT_PERFORMANCE.md` §1 (the server-side symptom)

### Fixed

- **Salvaging did nothing, activating a consumable never spent it, and a vendor's Buy button flashed red without charging or granting: three inventory actions broken at three different layers.** The salvage log said it plainly — `Unhandled message BaseController::SalvageRequest` — there was no handler at all: `BaseController` now answers `SalvageRequest` through the new `Systems/Salvage/SalvageService`, which mirrors the wire shapes exactly (equipment travels by guid, one entry per piece; stackables travel guidless — a captured request for twenty health packs is literally `guid 0, sdb 82604, quantity 20`), refuses anything `RootItem.SalvageRewards` does not name (and any guid that is not carried, not that item, or equipped) by dropping just that entry from the `SalvageResponse` echo, and rolls what an item breaks into straight out of the database: `SalvageRewards` → the loot table, once per salvaged piece, through the new `SalvageRoller`. The roller carries both roll semantics the data authors: the token machines' mode 0 (one weighted pick) is left to `VendorTokenRoll`, while the salvage trees' modes 2-4 roll *every* row independently at `probability` percent - every full 100 guarantees rolls and the remainder is the chance of one more, which is both what `SalvageDisplayItems` calls `guaranteed` on its probability-100 rows and why the Tier-1 weapon table lists the same generic-parts sub-table six times at exactly 100. The consumable half had its own hole: the aptitude chain's server-side `ConsumeItem` command was an admitted placeholder (`Aptitude command … of type ConsumeItem (server) is not implemented server-side, using a placeholder` in the log), so a health pack fired its effect and cooldowns but stayed in the bag forever; the command is now implemented against the inventory (the activation carries the consumable's sdb id as its module) and `ActivateConsumable` refuses the activation up front when the player does not actually hold one, answering `AbilityFailed` instead of running free effects. And the Buy button: its red flash was the client enforcing its own bag model — `BagInventorySettings` was answered with a hardcoded snapshot of a developer's inventory, 207 phantom slots out of the 225 the client believed it had, so any real inventory bigger than the leftovers read as full and a purchase failed client-side without a request on the wire (which is why the two buys that *did* reach the server in the log succeeded, and currency visibly "wasn't taken" for the rest). The update is now built from the real inventory by the new `BagInventoryLayout` (the captured nine-bag layout, grown in whole 5-wide rows when the content needs it, slots mirrored items-first then stackables), goods that live in stacks on live - consumables, currency-style basics, raw materials - top up their resource pool instead of spawning non-stacking guid copies (`ItemStacking`, shared by vendor grants, salvage grants and the hardcoded fallback inventory), and `NpcVendorService.TryPurchase` declines a purchase that provably cannot fit *before* the currency moves, with `INVENTORY_FULL`, so the window shows a reason rather than flashing red and keeping the wallet. Tests: `SalvageServiceTests` (+8: guid/stack/mixed batches, all-or-nothing quantities, refusals), `SalvageRollerTests` (+6: guaranteed rows, min-0 rows, weighted picks, repeated sub-table rows, the cycle guard, missing tables), `ConsumeItemCommandTests` (+4), `BagInventoryLayoutTests` (+4), `NpcVendorServiceTests` (+3: stackable grants top the pool up, full bags decline without charging, one free slot fits again).

- **A shard that finished loading its chunks never finished loading, so every client was refused with "server not ready (zone still loading)" for as long as it was left alone.** The console said the truth and pointed at the wrong thing: `Zone 448: Loaded successfully in 00:01:00.7365562. Total statics: 1364781` and then nothing but refusals, because the last step of building the shard is baking the navigation mesh from every walkable collision triangle the zone has — millions of them on a prod zone — and `GameServer.Startup` sets `_isReady` only *after* the shard constructor returns. The bake itself was the problem: the two surface filters #106 added (`DropDuplicateOverlaps`, `DropStackedIslands`) each ran off an index that enters a face in **every cell its horizontal bounds cover**, and then scanned all the faces in the cells around each face's centroid. Ground is dense and triangles overlap each other's cells, so that is a few hundred candidate comparisons per face, twice, plus two more full index builds and a third build of the edge map (`BuildAdjacency` was run twice, and the adjacency only has to be built once for the pathfinder) — super-linear in a way that reads as a hang, with no log line between "Loaded successfully" and "navigation mesh has … faces" to say which step the process was inside. `NavigationMesh` now bounds every pass instead: duplicates are matched through a bucket of the face's own **quantised centroid** (two copies of a triangle have the same centroid; matching them by spatial overlap is what cost the neighbourhood scan), and the island test reads connected components straight from the edge map, judges only the patches small enough to be a canopy or a cavity at all (under 64 m on a side — a bigger disconnected layer is a bridge deck or a plateau, and `ACDisconnectedLayerTooBigToBeACanopyIsKeptWhateverSitsUnderIt` pins that it stays), and spends at most `IslandSupportCandidateBudget` (32 M) candidate comparisons over the zone, keeping whatever it did not reach and saying so in a warning. The edge map is collected once and re-keyed through the second pass's compaction (`Compact` now reports the survivor indices), and the runtime index clamps how many cells a single face may cover (`MaxIndexSpanCells`), which is also what keeps one absurd or non-finite vertex — a `float.NaN` casts to `int.MinValue`, and a cell loop from there to the other corner runs 4·10⁹ times per axis — from turning the bake into a permanent hang. The bake says what it is doing: `Zone {ZoneId}: baking the navigation mesh from {TriangleCount} collision triangles`, then the existing line with its face counts, now with the elapsed time. `GameServer` names the step in front of the shard constructor (`Starting shard for zone {ZoneId}: loading its collision and baking its navigation mesh; clients are refused until that finishes.`) and its refusal no longer claims a cause it cannot see ("the server is still starting; … see its last startup log line"). A model of the two passes over synthetic zones (clean ground, duplicated ground, and ground with 200–4000 scattered canopy patches) keeps exactly the faces the #106 version keeps while doing 25–100× fewer candidate comparisons — and none at all on a zone whose ground is one connected component, where #106 scanned every face against its neighbourhood to conclude the ground is not floating. Tests: `NavigationMeshTests` (+3: the absurd-span regression, duplicates far apart being left alone, the big disconnected layer); the existing four still pass off the same filter decisions. Docs: `Docs/WORLD_POPULATION.md` (what the mesh bake is bounded by, and why).

- **The Buy button in an NPC vendor window did nothing at all: no packet, no log line, no error.** The window opened, listed its stock and let a row be highlighted, and pressing Buy was silent — the client never sent `VendorPurchaseRequest`, so there was nothing server side to decline. The cause was the *size* of the ids the window was opened with. `VendorCatalog` minted product and price guids as `0x56454E44_xxxxxxxx` ("VEND" + vendor id + stock index, ≈6.2e18) and `NpcVendorService` answered `VendorProductsResponse.Id` with the vendor NPC's 64-bit entity id. The client carries those ids through its scripted UI, where every number is an IEEE-754 double with a 53-bit mantissa, and hands them back to the native layer when Buy is pressed; above 2^53 the round trip is lossy — at 6.2e18 the spacing between representable doubles is 1024, so an entire vendor's stock collapses onto one value and the id the UI returns no longer matches the entry it came from, and the purchase is dropped before it reaches the wire. The evidence is a live session in `themeldingwars/Documentation`'s `Captures/2015-05-02 - 1869 - Gameplay.pcapng.gz` (build 1869, "Copacabana ARES Supplies", terminal 60): one `VendorProductRequest`, one 3,006-byte `VendorProductsResponse` across three GSS fragments, and three purchases — with product guids 469931..603221, price guids 1229621..1334821 and store id 2321, i.e. plain database ids below 2^21, echoed back byte for byte in the purchases. `VendorCatalog` now mints guids below 2^26 (8 bits of stock index, 16 bits of vendor id, bit 24 flagging a price, bit 25 set so that none is ever zero) and `VendorCatalog.StoreId` supplies a small window id, so everything a window carries round-trips exactly through a double and through a 32-bit intermediate; `TryDecodeGuid` rejects anything using bits outside that encoding, the old oversized guids included. - Fix Charge leaving the camera look locked after the server cleared the effect: `CharacterEntity.SetStatusEffect` / `ClearStatusEffect` now also write the owner-private `Character_LocalEffectsController` slots, and `BaseAptitudeEntity.AddEffect` sends the real effect stack count ([#10](https://github.com/kasperfriend/PIN/pull/10))

#### Combat, health and damage

- Fix the first hit after a respawn instantly downing the character again: `NetworkPlayer.Respawn` wrote the reset health only into the replicated controller props while the entity stayed at 0 HP; it now resets vitals through `CharacterEntity.SetMaxHealth`/`SetCurrentShields` so server state and client view agree
- `DamageSystem` no longer damages or heals characters that are not in the `Living` state (corpses and bleeding out characters were fully damageable before), and `EntityDamagedEvent`/`EntityHealedEvent` are only published when the damage/heal actually applied
- `CharacterLifecycleService` only transitions out of the `Living` state now, so stray damage events can no longer skip the bleedout phase or double-fire death transitions
- Respawn and teleport reset the fall damage tracker, so stale fall speeds cannot deal damage at the destination
- `CombatSim.OnProjectileHit` no longer dereferences a null target or source when the hit cannot be resolved from the shard, and drops hits where the source's stance towards the target is `Friendly` or `Self` ([#1](https://github.com/kasperfriend/PIN/pull/1))
- `EntityManager.SendToScoped` no longer throws `KeyNotFoundException` for entities that were never scoped (a latent crash, reachable through `HitFeedback`)

#### Characters and login

- Fix the character selection screen and the in-game character not matching (selection showed a female Raptor while the game spawned a male Mammoth, because the two were built from separate hardcoded blobs and the gRPC lookup that was meant to reconcile them had no server implementation)
- Decode the zone id from the character guid on **both** the remote and the fallback login path - the 38 "characters" in the selection list are really zones, and only decoding it on the fallback path meant a working gRPC call would have dropped every entry into the same zone

#### Startup, configuration and build

- Fix Firefall auto-detection failing for every Steam library listed in `libraryfolders.vdf` (Steam stores the library root folder such as `D:\SteamLibrary`, not the `steamapps` folder, so all entries were rejected)
- Find Steam installations outside `Program Files` through the Windows registry, and standalone Firefall installs under `Program Files`
- Stop empty values in `GameServer.config.json` from overriding paths configured in the legacy `App.config`
- Fix WebHostManager startup crash (missing `Serilog.Enrichers.Context` and other Serilog extension assemblies when the servers are published into a single folder) by referencing the shared Serilog packages ([#6](https://github.com/kasperfriend/PIN/pull/6))
- Fix the Release workflow passing an empty `--prerelease` argument to `gh release create`, which gh treated as an asset glob and made release creation fail with `no matches found for ''` ([#4](https://github.com/kasperfriend/PIN/pull/4))
- Fix `CS1736` in `EntityManager.SpawnCharacter` (`Quaternion.Identity` is not a compile-time constant, so it cannot be a default parameter value) ([#3](https://github.com/kasperfriend/PIN/pull/3))
- Fix `CS0718` / `CS1503` build errors in `FirefallInstallLocator` (static class used as a `ForContext<T>()` type argument, then a bare-string `ForContext` overload that does not exist) ([#7](https://github.com/kasperfriend/PIN/pull/7), [#8](https://github.com/kasperfriend/PIN/pull/8))
- Make the server handling code more robust
- Many improvements in the entity definitions

### Known limitations

- NPC movement is horizontal only: `SnapToGround` is implemented but **off by default**, because nothing in the repo pins down whether a character origin sits at the feet or at the centre of the body. It is a one-line rule flip plus a `GroundOffset` once that has been confirmed in game (see `Docs/NPC_AI.md`)
- NPC AI tuning (the 180 damage / 1.2 s attack cadence and the `CurrentPoseUpdate` broadcast rate) has not been validated against a running client — it needs in-game play, not CI
- ~180 aptitude commands are still `Todo/` placeholders. `Factory` now logs each one it falls back on, so `\abilityinfo` shows exactly which command a cosmetic ability is waiting for
- 14 identified `dbcharacter` tables (`MonsterVisualOption`, `MonsterMood`, `MonsterItemTags`, `MonsterTitle`, `TurretWeapon`, `VoiceSet`, …) are still unread; they are listed in `Docs/STATIC_DATABASE.md` as the next targets
- The patched `FirefallClient.exe` is not built by CI and must be attached to each release manually (README step 6)
