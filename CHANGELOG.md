# Changelog

## [Unreleased]

### Added

- Add the AI's melee model and its damage conversion as pure, testable pieces: `Systems/Ai/AiAttackDamage.cs` (`AiAttackDamage.Resolve(damageRating, fallback, fraction)` — a monster's `dbcharacter::MonsterScaling.damage` rating -> what one swing is worth, with a documented rationale for why the column is a rating and not a per-hit amount) and `AiVectors.Distance` / `AiVectors.HeightDelta` (straight-line 3D distance and absolute height difference next to the horizontal distance the brain already used to plan walking). `IAiRules` gained `MaxAcquisitionHeightDelta`, `MaxAttackHeightDelta` and `AttackDamageFraction`, and `AiPerception` gained `AttackDistance` and `HeightDeltaToTarget`, so the reach and height-band rules live in `AiBrain` where `AiBrainTests` covers them instead of in the shard code

- NPC combat stats are now served from the static database end to end: `CharacterEntity.LoadMonster` resolves the level of the shard zone's level band (`dbzonemetadata::ZoneRecord.level_band` -> `dbitems::LevelBand`, top of the band, `255`-sentinel/open bands resolve to their floor, capped at the 80-row `dbcharacter::MonsterScaling` table; zones without a band fall back to `SDBUtils.DefaultNpcLevel`) and spawns the NPC with that row's `health` as `MaxHealth`. The AI engine resolves each NPC's per-hit attack damage from the same row's `damage` once at `AiEngine.Register` (`IAiMonsterStats.GetAttackDamage(typeId, level)` -> `SdbAiMonsterStats`) into the NPC's brain, and `ResolveAttack` applies it; `StandardAiRules.AttackDamage` is now only the fallback when the database has no row, mirroring the level fallback. Band -> level rules are pure and unit tested (`NpcLevelResolutionTests`), and `AiEngineTests` cover the DB-damage-beats-fallback and fallback-on-missing-row cases. Docs: `Docs/NPC_AI.md` §5 ("Health and attack damage come from the database"), `Docs/SPAWNING_AND_COMBAT.md`, `Docs/MOBS_AND_NPCS.md`, `Docs/SpawnReference/MOBS.md`
- The band-less-zone NPC fallback now follows the actual default player level: `SDBUtils.DefaultNpcLevel` is 1 (a fresh battleframe's progression level) instead of the retired hardcoded player level 45, so zones the database never tuned — the PIN test zone 12 "Nothing", Crash Down 1003 and the mission pockets whose difficulty the live game set through its server-side spawn/mission flow (`dbcharacter::Monster` rows carry no level at all; only 55 of 3,109 reference a band) — spawn mobs on a fresh player's terms (level 1 = 100 HP, 50 per hit) instead of level-45 mobs that one-shot them. Mirroring that live spawn flow, `character_spawn.json` entries now take an authored `level` (1–80; 0 = resolve from the zone) that becomes the spawn's `MonsterScaling` level before any `max_health` override, and the stale `HardcodedCharacterData.Level`/`EffectiveLevel` constants are gone. Docs: `Docs/NPC_AI.md` §5, `Docs/SPAWNING_AND_COMBAT.md`, `Docs/PLAYER_STATS_AND_HEALTH.md` §3/§4, `Docs/SpawnReference/MOBS.md`
- Player weapon damage is now database driven: `WeaponSim.OnFireWeaponProjectile` resolves the per-round damage from the weapon item's own `Damage Per Round` attribute (954, whose `dbitems::AttributeDefinition` display name is "Damage Per Round"; e.g. the Accord Assault plasma cannon 86742 = 100, the Recon R36 86969 = 39) with the resolved weapon template's `damage_per_round` as the fallback (the value NPC weapons fight at) and `ProjectileSim.LegacyPlaceholderDamage` (1337) only for rows with neither. `ProjectileSim` now tracks the distance each projectile travels and applies the fired ammo row's falloff at impact: `damage_decay = 0` keeps flat damage; otherwise damage stays full until `damage_decay_rangefrac` of the weapon's range and then tapers linearly to `min_damage_frac` x per-round damage at max range (e.g. PvE assault-rifle ammo: full until 70% of the range, 33% at the edge). Rules are pure and unit tested (`WeaponDamageMathTests`). Docs: `Docs/SPAWNING_AND_COMBAT.md` §3/§4, `Docs/PLAYER_STATS_AND_HEALTH.md`
- Add `Docs/PLAYER_STATS_AND_HEALTH.md`, the audit of how every player stat is (or is not) served from the static database in build `prod-1962`: the replicated item-attribute stat sheet is the sum of the equipped items' `AttributeRange` rows, weapon damage is item attribute 954 "Damage Per Round" with ammo-defined distance falloff, and the health pool is item Health + the per-level `LevelItemAttributes` curve (see the max-health bullet); it also records what the database still does *not* define (per-frame base health: `Battleframe.base_health` is 0 on playable frames and the Health attribute is 100 on every frame; the original community-documented formula `((Base Health + Core Health) x Frame Health Bonus) x Level Modifier` cannot be fully rebuilt from rows alone) and what that means for the remaining constant

A fresh frame at level 1 has no curve (the table is 0 below level 4), so its pool is exactly its item sum (~360 for the default Accord loadout) — the strict "frames start at level 1" state; `HardcodedCharacterData.MaxHealth` (19192) survives only as the pre-loadout construction default and as the pool NPCs keep when `MonsterScaling` lacks their level. `dbitems::LevelItemAttributes` is now loaded by the static DB (it was not before). Rule is pure and unit tested (`CharacterHealthMathTests`). Docs: `Docs/PLAYER_STATS_AND_HEALTH.md` §4/§5

### Changed

- The shard loop is paced instead of spinning. It ran unbounded — a full core at 100% even on an idle shard, and the usual PIN setup runs the server and the game client on the same machine, so the spin came straight out of the client's frame budget. `Shard.RunThread` now targets a 5 ms cadence with a hybrid wait (coarse `Thread.Sleep` while a comfortable margin remains, `SpinWait` for the last ~2 ms); every subsystem is gate- or accumulator-driven, so a late iteration only shifts gate boundaries, and the fastest gate (the 5 ms entity update flush) keeps its intended rate. This also makes the loop's per-iteration subsystem calls 200 per second instead of tens of thousands
- The network tick ran every ~50 **microseconds** instead of every 50 ms: `ShouldNetworkTick` compared `_networkTickRate = 1.0 / 20.0` — a value in seconds — against a delta in milliseconds, so the gate was always open and every client's queues were drained, flushed and acked on virtually every spin of the loop. The gate is now `_networkTickIntervalMs = 10.0`, milliseconds on both sides: twice the cadence the constant was meant to express, bounding a movement confirm (MovementInput → ConfirmedPoseUpdate on the wire) to ≤ 10 ms of queueing
- Dead clients are now retired. Nothing removed a client that vanished without a `CloseConnection` (crash, network drop, alt-F4): it stayed in the client map and scoped to every entity it could see, so pose broadcasts and view flushes kept allocating and sending to a ghost forever — and `NetLastActive` could never notice because *sends* keep refreshing it. `NetworkClient` tracks a receive-only `NetLastReceive`, and `Shard` sweeps every 5 s: a full 60 s of one-way receive silence sends a best-effort `CloseConnection` and runs the normal `MigrateOut` cleanup (test fakes, which are not `NetworkClient`s, are skipped)
- The UDP sockets disable `SIO_UDP_CONNRESET` on Windows (Linux never had the behaviour): Windows surfaces the ICMP port-unreachable of a peer that vanished as a `WSAECONNRESET` error on the socket's next `SendTo`/`ReceiveFrom`, so every send to a dead client threw and logged until the sweeper above noticed. Best-effort with a fallback to the existing error handling on platforms where the ioctl is unavailable
- `BaseAptitudeEntity.GetActiveEffects()` fast-paths the empty case. The 32-slot copy (nulls included) ran for every entity on every 20 ms ability-system tick and again for each aptitude command touching effects — the biggest single allocator on a populated shard. Callers all null-check each entry, so an empty list is exactly what the all-null copy gave them; entities with at least one effect still get the same snapshot as before
- Queued scope-ins are sent in batches of 16 per 20 ms gate instead of one per gate: a login in a populated area streamed the surrounding entities in at 50 per second — seconds of visible pop-in — where the batch finishes a typical login's scope-ins in well under a second at the same reliable-channel pacing
- The physics dispatcher fleet is capped at 4 threads. A zone shard's 20 Hz timestep of mostly static geometry plus a few hundred kinematic bodies does not keep a large fleet busy — every Bepu dispatch thread is a spinning worker competing with the game client for a core (`ProcessorCount - 2` of them on a typical machine), and the same server-plus-client-on-one-machine setup pays for all of them

### Fixed

- Spawning a chassis-less monster no longer crashes with `NullReferenceException` in `PhysicsEngine.GetCharacterPoseAsset` (`spawn monster <id>` logged "HandlePacket Caught Object reference not set..." and the entity never appeared). `ApplyLoadout` builds the `CharacterCollisionComponent` only inside its `chassis.SdbId != 0` block — the only assignment of `CharacterEntity.Collision` in the codebase — so any `dbcharacter::Monster` row without a battleframe chassis (most creatures, which point at their pose type directly through the row's own `posetype_id` instead of a chassis) spawned with a null `Collision`, and `CreateKineticEntity` dereferenced `Collision.PoseTypeRecord` unguarded. `LoadMonster` now synthesizes the component from the Monster row's `PosetypeId` (scale from `MinRandScale`) when `ApplyLoadout` left it unset, installing an empty component (physics fallback sphere + a warning) when the row has no usable pose reference either; `GetCharacterPoseAsset` itself additionally treats missing `Collision`/`PoseTypeRecord` as "fallback shape" so a bad row can never take the packet handler down — which also guards `UpdateEntity`, which calls the same method
- The WebHostManager web hosts no longer answer every request with a 500. `WebHost.ClientApi`'s api/v3 controllers declare routes with an inline `{characterId:ulong}` / `{armyId:ulong}` constraint (`api/v3/characters/{characterId:ulong}/garage_slots`, `api/v3/armies/{armyId:ulong}/members`, inventories, login streak, …), but ASP.NET Core routing ships no `ulong` constraint — its built-in integer constraints stop at `int` and `long` — so building the endpoint matcher threw `The constraint reference 'ulong' could not be resolved to a type`. The matcher builds lazily, on the host's first request, so the host started fine and then failed *every* request, which took out the whole login flow served by the same host (`/api/v2/accounts/login`, `/api/v1/login_alerts`, `/api/v1/client_event`) and left the Firefall client stuck at the login screen. `Shared.Web.BaseWebServer` now registers a `ULongRouteConstraint` in `RouteOptions.ConstraintMap` for every web host, so the templates work as authored: the parameter matches only values that are (or invariant-culture parse as) an unsigned 64-bit integer, mirroring the framework's own `LongRouteConstraint`
- Fresh characters no longer zone in with the flat 19,192 HP construction default: `NetworkPlayer.Respawn` — which also runs on the first `ScheduleUpdateRequest` of a login, i.e. right when the client finishes loading the zone — used to reset the pool to `HardcodedCharacterData.MaxHealth`, stomping the DB-derived value `ApplyLoadout` had computed at login (which is why a fresh frame sat at ~19k HP until `setlevel` re-derived it, and why dying and respawning after `setlevel 45` threw the pool back to the flat default). It now resets through `CharacterEntity.ResetMaxHealthFromDatabase` — the same loadout item-Health + frame-level curve rule — followed by an explicit fill, so every respawn comes back at full health of the database-derived pool (level 1 = the item sum, ~361 for the default Accord Assault loadout). The rest of the spawn-path stats were audited and are already correct by construction: the stat sheet, weapon arrays and energy params are (re)built by `ApplyLoadout` from the database on login and are not touched by respawn, level props replicate `FrameProgressionLevel` (1) from construction, and shields stay 0 because the build has no shield item attribute. `CharacterEntityHealthTests` gains the regression tests (`ResetMaxHealthFromDatabase` replaces the construction default at level 1, folds in the level-45 curve at the documented ×3 scale, and leaves a source-less pool untouched). Docs: `Docs/HEALTH_SYSTEM.md` §1, `Docs/PLAYER_STATS_AND_HEALTH.md` §4/§5
- Audit-and-fix pass over the whole solution for crash paths and hot-loop waste. Every fix below was checked against the existing tests; none changes a pinned behaviour.
  - A single malformed or racing packet could take the whole process down: `PacketServer.ServerRunThreadAsync` is an `async void` worker, so an exception out of `HandlePacket` escaped to the runtime instead of skipping a packet — the shard thread got this exact treatment earlier, the packet pump now gets it too (per-packet `try`/`catch` that logs the endpoint and keeps the queue draining; GameServer and MatrixServer both inherit it)
  - `GameServer.RetrieveClient` raced on first contact: `ContainsKey` + indexer could throw `KeyNotFoundException` if a disconnect removed the client between the two lookups, and `AddOrUpdate` + `MigrateIn` from a losing thread could migrate the winner's player a second time. Now one `TryGetValue`, a `TryAdd` (only the inserting thread migrates), and a safe read-back for the lost race
  - `NetworkPlayer.Login` was `async void` with an `await` inside: any exception after the GRPC character fetch (e.g. the outpost lookup below) escaped into the thread pool and killed the server process. The interface method now fires a `Task` that catches, logs, and sends `CloseConnection` on that one connection instead
  - `NetworkPlayer.FindClosestAvailableOutpost` indexed `outposts[targetOutpostId]` with an id that comes from persisted character data (`LastOutpostId`): an outpost the zone no longer has threw `KeyNotFoundException` through login's continuations. It now falls back to the zone's default outpost
  - `GenerateServerId` read two uninitialized stackalloc bytes into the server id (`stackalloc` is not zeroed; only bytes 2..7 were filled). The buffer is cleared first, and the id uses `Random.Shared`
  - A chat message of just `\` (backslash, nothing after it) threw `IndexOutOfRangeException` in both command parsers (`parts[0]` of an empty `Split` result) through that client's network tick. An empty command line now resolves to the normal "Unknown command" reply (`ChatCommandService`, `AdminService`)
  - Army GRPC events (`ArmyIdChanged`, `ArmyTagUpdated`, army-member filtering) dereferenced `player.CharacterEntity` for players that are still mid-login — a `NullReferenceException` on the GRPC stream thread that tore down the event stream until the 30 s retry. The handlers now skip members without an entity
  - The GameServer's REST mock endpoints `ulong.Parse`d route values (`characters/{id}/inventories/...`, `armies/{id}/...`, `garage_slots`, `login_streak`): any non-numeric id produced an unhandled `FormatException` (HTTP 500). The routes carry the `:ulong` constraint now, so a malformed id is a 404 like any other unknown route
  - `Shard.MigrateIn`/`MigrateOut` used check-then-act pairs on the concurrent client map (`ContainsKey` + `Add`/`Remove`); both are single atomic `TryAdd`/`TryRemove` operations now, so a double `MigrateOut` can no longer run the disconnect cleanup twice and a racing `MigrateIn` can no longer `Init` the same player twice
  - The GRPC retry loop logged "Failed to establish GRPC stream" without the exception and treated shutdown-token cancellations as failures to retry after another 30 s; it now logs the exception and stops on cancellation
- Fix homing projectiles flying at CPU speed. The shard loop spins between the subsystems' own gates, and `ProjectileSim.Tick` had **no** gate: it ran on every spin iteration, so a homing missile advanced a hardcoded `Velocity * 0.05f` (a 50 ms step) hundreds of times per real second — effectively instantaneous flight — while every other simulation mode re-derived its position from absolute elapsed time and only wasted the raycasts. `ProjectileSim` now steps at a 20 ms cadence (the ability system's rhythm; 50 Hz impact detection, segments still swept end-to-end by the segment raycast so nothing tunnels), integrates homing motion by the time actually elapsed since the previous step (clamped to 100 ms so a GC pause cannot teleport a missile), and enumerates the live projectile dictionary instead of allocating a `Keys.ToArray()` snapshot per tick. `UpdateIntervalMs` keeps the empty-shard early-out and refreshes the step clock between volleys
- `GameServer`'s UDP send thread copied every outgoing datagram with `PacketData.ToArray()` before `SendTo`; it now sends the packet's `ReadOnlySpan<byte>` directly — one full-sized allocation and copy removed per datagram on the hottest send path. The GSS packet demuxer likewise dropped a 7-byte array per packet (`Read(7).Span.CopyTo` + `BinaryPrimitives.ReadUInt64LittleEndian` instead of `ToArray()` + `BitConverter`)
- Aptitude chains were rebuilt from the static DB on **every** activation: commands only carry their immutable parameter record (all mutable state lives in the `Context`), so `Factory.LoadChain` caches built chains by id (`ConcurrentDictionary`, races collapse to one shared instance) and continuous activators — proximity effects, NPC and deployable abilities — stop re-allocating their whole command list each time they fire. `RegisterRandomCommand` accordingly draws from `Random.Shared` (a chain-cached instance is shared by the packet thread and the shard thread; an instance-field `Random` is not thread-safe). The per-command "resolved command" log of every activation moved from Information to Verbose, in line with the earlier finding that a busy shard's console is the slowest part of the tick loop
- Replication hot path: every `Channel.SendChanges`/`SendMessage`/`SendViewKeyframe`/`SendControllerKeyframe` call re-ran `GetCustomAttributes` (an attribute array allocation plus a type scan) — and view-change sends happen for every dirty view of every scoped entity on every 5 ms update flush. The two Aero marker attributes are now resolved once per message type through a static generic cache (`Channel.AeroAttributes<T>`) and read for free afterwards
- Entity scope checks ran an O(entities × players) scan with a lazy `Where` re-enumerated per entity and a `Vector3.Distance` (square root) per pair; the player snapshot is materialized once per pass and the comparison uses `DistanceSquared` against the squared threshold
- Fix mobs killing a level-45 player in four or five punches. `AiEngine` had been spending the monster's `dbcharacter::MonsterScaling.damage` value *directly* as one swing's damage, but that column is a per-level rating, not a per-hit amount: on all 80 rows it is exactly `round(MonsterScaling.health / 2)` (level 1 is 100 HP / 50, level 45 is 27,869 / 13,934, level 80 is 153,726 / 76,863) — the twin of the level's health, the same figure `dbcharacter::MonsterAttributeRange`'s 0.8-1.15 "Creature Damage Modifier" then scales, which is why a level-45 mob deleting a ~20k pool in one or two hits was arithmetic and not tuning. The AI now commits `StandardAiRules.AttackDamageFraction` (0.1) of the rating per swing through the new `AiAttackDamage.Resolve`: 1,393 a hit in a level-45 zone (~14 swings for a player with the ~19-21k that level's health rule gives), 5 at level 1 in the untuned zones, and the ratio holds across the table instead of only at the level the fix was tuned on. The rules' fallback `AttackDamage` also dropped from 180 to 5, which is the same fraction of the level-1 rating — an NPC whose monster row or scaling row does not resolve is a weak punch now instead of a siege weapon that takes a fresh frame's ~360 health pool in two hits. It is deliberately not applied to the fallback a second time. Tests: `AiAttackDamageTests` (new), the fraction/fallback cases in `AiEngineTests`, `StandardAiRulesTests`. Docs: `Docs/NPC_AI.md` §3/§5, `Docs/SPAWNING_AND_COMBAT.md` §3
- Fix enemies attacking from across the zone, and hitting players standing above or below them. `StandardAiRules.AttackRange` was 45 m with `AttackRangeExit` 52 — the range of a *shooting* NPC — while `AiEngine.ResolveAttack` damages its target directly, with no projectile in between, so a mob that merely saw you from 45 m punched you at full rate (`AttackDamage 1417 per attack (cooldown 1200 ms)` every tick of `\r 19` in the reported log, the player 402 m above the mob in Z). Attacking is now gated on a melee volume in `AiBrain`: the straight-line distance to the target must be inside `AttackRange` (3.5 m, modelled on the mob melee template's own 2.6 m range, with 2 m of vertical slack included), the target's height may not differ by more than `MaxAttackHeightDelta` (2.5 m — otherwise a player standing over the mob's head is 1 m away and gets hit through the floor), `StandoffRange` (2 m) is where chasing parks, and `AttackRangeExit` (5 m) is the only rule that breaks an attack, so backing off 4 m ends the fight while jitter on the boundary does not. Chasing still plans on the horizontal distance (straight-line distance makes a mob on a ridge 402 m away "far", which is the leash-free wandering that report also showed), and a candidate more than `MaxAcquisitionHeightDelta` (12 m) above or below is never acquired at all, so a mob on the floor does not lock onto a player on the roof over it and stand there with nothing to do — it loses the target instead. The aggro debug log reports the height it skipped, and the acquired-target log now prints flat + straight-line distance so the two numbers are not confused again. Tests: `AiBrainTests` (reach, height band, drop-out radius, no-attack-while-lost), `AiEngineTests` (a mob under a player never damages them, a mob 40 m away never damages them, a player 30 m up is not even acquired), `AiVectorsTests`, `StandardAiRulesTests`. Docs: `Docs/NPC_AI.md` §2/§3/§6, `Docs/SPAWNING_AND_COMBAT.md` §3
- Fix weapon damage not growing with the player's level — a rifle did the same 60 per shot at level 45 as at level 1. `dbitems::AttributeRange.per_level` is 0 on every one of the 954 rows, so the item attribute a shot is resolved from is a single number and nothing scaled it; what the database scales instead is the *item*: a weapon family has one preset item per level and their 954 values follow `x (2 * 1.05^(level-1) - 1)` exactly (verified row by row: the Accord Assault AR family 10020 runs 11 / 12.1 / 13.255 / 14.4677 ... 44.5929 for levels 1-20, the plasma family 10003 runs 100 / 110 / 120.5 / 131.525 ... 405.3901). `WeaponSim.ResolveRoundDamage` now applies that curve through the new `WeaponDamageMath.DamageLevelScale` to whatever damage source the shot resolved from — the item attribute, and equally the `WeaponTemplates.damage_per_round` fallback, which is the path an NPC's own level-45 preset feeds (the same selection that already picks 225 for a Melded Aranha over the 1 of a Chosen Fiend's stub) — because this build has no item-swapping progression flow, so a level-45 frame still carries its level-1 preset rows. `\level 45` now takes a 60-damage rifle to 967 and the level-1 plasma cannon to 1,611 per shot, while a fresh frame at level 1 is byte-identical (the scale is exactly 1.0 there). Headshot and crit multipliers and the ammo falloff keep applying on top of the scaled base (the falloff floor is a fraction of per-round damage, so it grows with it too); the 1337 `LegacyPlaceholderDamage` stand-in is deliberately not scaled (it is not a database value), and ability damage stays chain-register driven. Tests: `WeaponDamageMathTests` (the curve reproduces the real per-level rows; a level-1 shot costs exactly what the database says; a level-45 11-damage rifle round costs 177). Docs: `Docs/PLAYER_STATS_AND_HEALTH.md` §3, `Docs/SPAWNING_AND_COMBAT.md` §3/§4

- Implement the `TargetByExists` aptitude command (type 134, "Target - Filter Existing Objects", 135 chain instances in build `prod-1962`): it loaded as a placeholder that kept every target, so chains holding a target over time (effect update/duration chains, deployables, called-down vehicles, NPC chains) went on acting on entities that had already despawned; it now keeps only the targets still registered with the shard, moving the pre-filter list to the former targets like the other target filters
- Implement the `RequireInRange` aptitude command (type 81, "Requirement - In Range"): it loaded as an always-succeed placeholder, so chains gated on staying near their target (tethered buffs, beam-style heal/repair effects, interaction and NPC follow-up chains) kept running no matter how far the target ran off; it now fails when any current target is further than the def's `Range` from the entity running the chain, honours the `Negate` flag, leaves the target list untouched and keeps succeeding when the chain has no targets
- Implement the `TargetDifference` aptitude command (type 101, "Target - Difference", 21 chain nodes in build `prod-1962`): it loaded as a placeholder that only shuffled the two target lists around without ever subtracting anything, so both chain shapes that use it kept their full target list. It now drops every target that appears in both the current and the former list, honouring `SwapCurrentFormer` (subtract the current list from the former one instead, for the layered `TargetConeAE` blasts that need the ring between an outer and an inner volume) and `ReplaceFormer` (keep the unfiltered list as the former one). Periodic area chains that pop the previously hit set into the former list therefore act on the entities that *entered* the area since the last tick instead of re-applying to everybody standing in it, and ring blasts no longer hit their inner volume once per ring
- Add `AbilityState` / `AbilitySystem`, the per-entity tracker of ability cooldowns (local / category / global) and of the jetpack energy pool that the aptitude runtime had no notion of before
- Add the `\abilityinfo` chat command (aliases `\abi`, `\ability`, `\aptitudeinfo`): dumps every ability slot of the current loadout as `module id -> ability id -> chain`, and for each chain node prints the command type, its environment (`client`/`both`/`server`) and whether the runtime resolves it to a real command, an unimplemented placeholder or a client-only no-op, plus the player's server `AbilityState`
- Add `AbilityStateTests`, `TargetByExistsCommandTests`, `RequireInRangeCommandTests` and `TargetDifferenceCommandTests` to `GameServer.Tests`

### Fixed

#### Abilities

- Fix activated abilities (Raptor and every other battleframe) staying purely cosmetic: `InstantActivation`, the chain node that carries each ability's cooldown configuration, was an empty stub, so no cooldown was ever started, the client got an empty cooldown payload and the ability could be re-pressed forever
- Start activation cooldowns only after the whole ability chain succeeded (queued by `InstantActivation`, committed by `AbilitySystem.HandleActivateAbility`), so an ability that fails a later requirement does not go on cooldown
- Track the aptitude cooldown category per ability (learned from its activation command) instead of using `AbilityModule.UiCategory`, which is a UI grouping and never matched a real cooldown category
- Report category cooldowns to the client (`ActiveCooldowns_Group2`) and express the global cooldown window in shard time, so the client-side ability timers no longer jump
- Wire the aptitude register pipeline so data-driven amounts are computed correctly: `LoadRegisterFromStat` (aptitude stat modifiers, e.g. energy/cooldown), `LoadRegisterFromModulePower` (ability module power rating), and `PushRegister`/`PopRegister`/`PeekRegister` are now implemented and resolved in `Factory`; chains that multiply an SDB amount by a loaded value no longer collapse to 0
- Mirror the client recharge model in the server `AbilityState`: regeneration waits `EnergyParams.Delay` after the last spend, an overcharged (negative) pool keeps recharging back through zero, and `EnergyToDamage` converts the actual tracked pool instead of assuming a full one
- Keep ability energy client-simulated like the live game: abilities do not cost (or get gated by) the regular energy pool - only the jetpack/thrust drains it. Client-environment aptitude energy commands (`RequireEnergy`, `ConsumeEnergy`, `ConsumeEnergyOverTime`, `RequireEnergyByRange`) load as no-ops on the server again, and the hardcoded per-activation fallback costs were removed
- Derive the replicated jetpack energy parameters (`EnergyParams`: max, recharge rate, recharge delay) from the equipped battleframe's SDB record whenever a loadout is applied
- Log aptitude chain nodes that are still unimplemented server-side, so an ability that plays its animation but does nothing can be traced to the exact placeholder command
- Fix Charge leaving the camera look locked after the server cleared the effect: `CharacterEntity.SetStatusEffect` / `ClearStatusEffect` now also write the owner-private `Character_LocalEffectsController` slots, and `BaseAptitudeEntity.AddEffect` sends the real effect stack count ([#10](https://github.com/kasperfriend/PIN/pull/10))

#### Combat, health and damage

- Fix the first hit after a respawn instantly downing the character again: `NetworkPlayer.Respawn` wrote the reset health only into the replicated controller props while the entity stayed at 0 HP; it now resets vitals through `CharacterEntity.SetMaxHealth`/`SetCurrentShields` so server state and client view agree
- `DamageSystem` no longer damages or heals characters that are not in the `Living` state (corpses and bleeding out characters were fully damageable before), and `EntityDamagedEvent`/`EntityHealedEvent` are only published when the damage/heal actually applied
- `CharacterLifecycleService` only transitions out of the `Living` state now, so stray damage events can no longer skip the bleedout phase or double-fire death transitions
- Respawn and teleport reset the fall damage tracker, so stale fall speeds cannot deal damage at the destination
- `CombatSim.OnProjectileHit` no longer dereferences a null target or source when the hit cannot be resolved from the shard, and drops hits where the source's stance towards the target is `Friendly` or `Self` ([#1](https://github.com/kasperfriend/PIN/pull/1))
- `EntityManager.SendToScoped` no longer throws `KeyNotFoundException` for entities that were never scoped (a latent crash, reachable through `HitFeedback`)

#### Characters and login

- Fix the character selection screen and the in-game character not matching (selection showed a female Raptor while the game spawned a male Mammoth, because the two were built from separate hardcoded blobs and the gRPC lookup that was meant to reconcile them had no server implementation)
- Decode the zone id from the character guid on **both** the remote and the fallback login path - the 38 "characters" in the selection list are really zones, and only decoding it on the fallback path meant a working gRPC call would have dropped every entry into the same zone

#### Startup, configuration and build

- Find Steam installations outside `Program Files` through the Windows registry, and standalone Firefall installs under `Program Files`

- Fix WebHostManager startup crash (missing `Serilog.Enrichers.Context` and other Serilog extension assemblies when the servers are published into a single folder) by referencing the shared Serilog packages ([#6](https://github.com/kasperfriend/PIN/pull/6))

- Fix `CS1736` in `EntityManager.SpawnCharacter` (`Quaternion.Identity` is not a compile-time constant, so it cannot be a default parameter value) ([#3](https://github.com/kasperfriend/PIN/pull/3))
- Fix `CS0718` / `CS1503` build errors in `FirefallInstallLocator` (static class used as a `ForContext<T>()` type argument, then a bare-string `ForContext` overload that does not exist) ([#7](https://github.com/kasperfriend/PIN/pull/7), [#8](https://github.com/kasperfriend/PIN/pull/8))

### Known limitations

- NPC movement is horizontal only: `SnapToGround` is implemented but **off by default**, because nothing in the repo pins down whether a character origin sits at the feet or at the centre of the body. It is a one-line rule flip plus a `GroundOffset` once that has been confirmed in game (see `Docs/NPC_AI.md`)
- NPC AI tuning (the 180 damage / 1.2 s attack cadence and the `CurrentPoseUpdate` broadcast rate) has not been validated against a running client — it needs in-game play, not CI
- ~180 aptitude commands are still `Todo/` placeholders. `Factory` now logs each one it falls back on, so `\abilityinfo` shows exactly which command a cosmetic ability is waiting for
- 14 identified `dbcharacter` tables (`MonsterVisualOption`, `MonsterMood`, `MonsterItemTags`, `MonsterTitle`, `TurretWeapon`, `VoiceSet`, …) are still unread; they are listed in `Docs/STATIC_DATABASE.md` as the next targets
- The patched `FirefallClient.exe` is not built by CI and must be attached to each release manually (README step 6)
